# 모바일 반응형 구축 실행 계획

- 작성일: 2026-09-07
- 대상: `apps/web`의 공개·인증·관리자 화면
- 실행 예정 모델: GPT-5.6 Luna
- 문서 성격: 모바일 재설계 실행 계획. 실제 진행·검증 상태는 이번 작업의 감사·구현 기록에서 확인한다.
- 목적: 모바일에서 탐색, 열람, 작성, 참여, 관리 업무를 편리하게 수행하도록 정보 구조·상호작용·시각 디자인을 개선한다. 이미 구현된 화면도 더 나은 결과가 확인되면 구조부터 재설계한다.
- 최신 사용자 방향(2026-09-07): “모바일 페이지가 이미 구현되었더라도 확실히 더 모던하고 좋은 방향으로 수정 가능하다 싶으면 뜯어고치는 방향.” 아래의 재설계 원칙은 초안의 기존 모바일 구현 유지·최소 수정 원칙보다 우선한다.
- 기준 정정(2026-09-08): 과거 프로젝트 문서의 디자인 규칙·요구사항·수정 이력은 참조하거나 복원하지 않는다. 현재 코드·실제 화면·사용 흐름과 이번 대화의 재설계 방향을 기준으로 판단한다.

## 1. 범위와 진행 원칙

1. 공개·인증 화면을 1차 완료 범위로, 관리자 화면을 2차 완료 범위로 진행한다. 전체 반응형 완료는 두 범위의 검증까지 포함한다.
2. React·TypeScript·Tailwind와 기존 디자인 시스템을 기반으로 한다. 필요하면 공통 컴포넌트, 토큰, DOM 구조, 모바일 전용 표시 컴포넌트를 재설계한다. 동일한 route와 업무 로직을 공유한다.
3. 모바일의 정보 우선순위, 섹션 순서, 탐색 메뉴, 카드/목록, 상세 표시, 조작 위치는 재설계할 수 있다. 데스크톱은 회귀 검증 대상으로 삼아 이번 개선으로 의도하지 않은 변화가 생기지 않게 한다.
4. API, 인증, 권한, 제출 조건, 응답 데이터 형식, 주요 기능 접근을 유지한다. 표시 컴포넌트를 교체해도 상태·핸들러를 공유하고 입력·선택의 연속성을 보존한다.
5. 과거 프로젝트 문서의 배치·표현·유지·변경 보류 지침은 판단 근거에서 제외한다. 현재 기능·데이터·권한과 서비스 식별에 필요한 브랜드 요소를 파악하되, 기존 외형 자체를 정답으로 취급하지 않는다.
6. 화면이 깨지지 않아도 탐색 비용, 정보 우선순위, 읽기 흐름, 조작 편의, 시각적 일관성이 부족하면 개선 대상으로 삼는다. 큰 변경은 설계한 화면/컴포넌트 단위로 교체하고, 교체 후 사용하지 않는 스타일과 중복 UI를 함께 정리한다.
7. 단순 배치는 CSS로 처리한다. JS 분기는 실제 상호작용이 달라지는 경우에만 사용하고, 리사이즈로 입력 상태가 초기화되지 않게 한다.

판단 근거: 현재 코드·설정·브라우저 실측·실제 콘텐츠·이번 사용자 지시. 이번 모바일 작업에서 작성한 감사·목표안은 근거와 진행 상태를 이어받는 용도로 사용하며, 코드가 바뀌면 영향을 받은 판단만 재검증한다. 과거 프로젝트 문서로 돌아가 디자인 규칙을 가져오지 않는다.

### 1.1 유지·개선·재설계 판단

모든 모바일 화면에 아래 판정 중 하나를 기록한다. “이미 반응형이다”는 유지의 충분한 근거가 아니다.

| 판정 | 판단 근거 | 실행 범위 |
|---|---|---|
| 유지 | 핵심 정보와 액션이 잘 읽히고 실제 흐름이 편리하며, 대안의 개선 효과가 작음 | 필요한 회귀 검증과 일관성 조정 |
| 개선 | 정보 구조는 적절하나 여백·타이포·밀도·상태 표현·조작 영역에서 개선 여지가 있음 | 컴포넌트 스타일과 일부 배치 수정 |
| 재설계 | 메뉴/목록/편집 구조 때문에 탐색·읽기·조작 비용이 높거나, 대안이 더 명확한 정보 위계와 일관된 화면을 제공함 | 섹션 재배치, 새 모바일 표현, 컴포넌트 교체 및 관련 CSS 정리 |

- 명백한 가로 넘침이나 클릭 불가 버그가 없어도 재설계할 수 있다. 긴 메뉴에서 원하는 기능을 찾기 어렵거나, 카드 장식이 정보보다 크거나, 한 화면의 강조 수준이 같아 핵심 행동이 안 보이는 경우도 근거가 된다.
- 재설계 후보는 기존안과 목표안을 같은 데이터·언어·화면 폭으로 비교한다. 실제 사용 흐름의 단계 수, 주요 정보/액션까지의 스크롤, 정보 탐색의 명확성, 읽기 편의, 터치 조작, 시각적 일관성을 근거로 삼는다.
- 사용자 데이터나 실험 없이 사용자가 선호한다거나 전환율이 올랐다고 단정하지 않는다. 시각적 판단은 비교 화면과 판단 이유를 남긴다.
- 기존안을 억지로 유지하지도, 변화량을 늘리기 위해 교체하지도 않는다. 목표안을 채택하면 그 구조를 완성하고 기존 UI 위에 임시 override를 계속 쌓지 않는다.
- 이번 요청은 모바일 UI 재설계를 계획에 포함하라는 허용이다. 이후 해당 구현 단계가 요청되면 이 범위의 디자인 변경마다 다시 승인을 묻지 않는다. 이번 턴은 계획서 수정까지만 진행한다.

### 1.2 이번 프로젝트에서의 모던한 모바일 디자인

- **정보 위계:** 페이지의 핵심 목적, 제목, 상태, 주요 행동이 순서대로 읽히게 한다. 중요하지 않은 메타·보조 액션은 필요한 맥락에 배치한다.
- **일관된 화면 구성:** 여백·글자 크기·모서리·아이콘·상태 색을 공통 역할로 정리한다. 목록은 구분선 중심, 카드와 시트는 내용 묶음과 작업 전환이 필요한 곳에 사용한다.
- **모바일 탐색:** 메뉴에 링크를 모두 늘어놓는 방식, 가로로 긴 탭, 화면 상단의 여러 도구를 실제 사용 흐름에 따라 재구성한다. 목적지가 숨겨지거나 불필요한 단계가 늘지 않게 비교한다.
- **자연스러운 조작:** 선택 영역 전체 터치, 읽기 쉬운 오류 안내, 필요한 위치의 액션, 입력 중 상태 유지와 복귀 동작을 갖춘다.
- **콘텐츠에 맞는 밀도:** 제목을 지나치게 자르거나 글자를 줄여 맞추지 않는다. 반대로 장식과 과도한 여백이 정보를 밀어내지 않게 한다.
- **절제된 피드백:** 상태 변화와 선택 결과를 분명히 표시하고 모션은 전환을 이해하는 데 사용한다. 기존 SOC의 중립색·브랜드 포인트와 reduced-motion을 반영한다.
- 하단 내비게이션, sticky CTA, 전체 화면 메뉴, 바텀시트는 후보 패턴이다. 주요 목적지 수, 사용 흐름, 키보드·채널톡·safe area 충돌을 검토해 채택한다. 유행하는 패턴 자체를 목표로 삼지 않는다.

## 3. 화면 폭과 공통 동작 기준

### 화면 폭

| CSS viewport 폭 | 기본 동작 |
|---|---|
| 320–639px | 1열 본문, 긴 액션 행은 줄바꿈, 카드/본문은 화면 안에 배치 |
| 640–767px | 긴 입력 영역은 1열 유지, 짧은 카드·설정만 충분한 폭에서 2열 |
| 768–1023px | 태블릿. 2열은 콘텐츠가 들어갈 때만 사용하고 편집기·표의 가독성 우선 |
| 1024–1279px | 기존 lg 레이아웃과 공개 헤더의 모바일 메뉴를 출발점으로 삼고 목표안에 맞는 전환점 검증 |
| 1280px 이상 | 기존 데스크톱 GNB 및 화면별 다열 레이아웃 유지 |

이는 기존 `sm/md/lg/xl` 사용을 정리하기 위한 출발점이다. M00에서 실제 생성 CSS와 설정을 확인한다. 목표안에 더 적합하면 헤더를 포함한 전환점을 변경할 수 있으며 경계 폭을 검증한다. 모든 컴포넌트의 전환점을 일괄 통일하지 않는다.

### 공통 완료 기준

- 320px 이상에서 문서 전체의 가로 스크롤이 발생하지 않는다. 허용한 표·코드·탭·캐러셀 내부 스크롤은 예외다.
- 기존 좌우 여백 토큰을 기본으로 사용하고, 320–359px에서 필요하면 좁은 화면용 `1rem` 여백 토큰을 적용한다.
- 모바일 주요 버튼, 아이콘 버튼, 탭, 선택 항목의 실제 터치 영역은 `2.75rem` 이상을 목표로 한다. 기존 34–40px 시각 크기는 주변 클릭 영역 확장으로 보완할 수 있다. 클릭 영역끼리 겹치지 않아야 한다.
- 본문·레이블의 의미 기반 타이포 토큰을 사용한다. 모바일 입력 글자는 `1rem`을 기본 제안으로 검증하며, 루트 글자 크기를 줄여 화면을 맞추지 않는다.
- 긴 한국어 제목, 영어 단어, URL, 파일명에 각기 적절한 줄바꿈/말줄임 규칙을 적용한다. 상세에서 원문을 읽을 수 있어야 한다.
- 전체 화면 팝업과 메뉴는 동적 viewport 및 safe area를 고려한다. 입력 키보드가 열린 상태는 별도로 검증한다.
- 채널톡은 기본 launcher를 유지하고 마지막 콘텐츠·제출 버튼·페이지네이션과의 충돌을 화면별로 검증한다. 기존 `.channel-talk-safe-area`의 하단 예약 공간부터 활용한다.
- 메뉴·모달은 열기, 내부 스크롤, 닫기, 포커스 복귀를 제공한다. 모달인 경우 배경 상호작용 차단과 포커스 가두기를 적용한다.
- 한국어·영어, 로그인 전·후, 로딩·빈 결과·오류·긴 콘텐츠 상태를 포함한다.
- 재설계한 화면은 정상 렌더링 외에도 M00-D에서 정한 개선 목표를 만족해야 한다. 전후 비교에서 얻은 이점과 불리해진 점, 그 보완 결과를 기록한다.

## 4. Luna 실행 단위

한 번에 아래 작업 ID 하나를 진행한다. 허용 파일이 많아지는 작업은 표에 제시한 하위 순서로 나누어 진행한다. 이는 모델 성능에 대한 가정이 아니라 변경 범위와 검증 결과를 추적하기 위한 작업 방식이다.

### M00 — 기준 화면·문제·개선 기회 확보

- 읽을 곳: 현재 `App.tsx`, 공통 UI, 스타일·토큰, web 스크립트·설정. 과거 디자인·제품·감사 문서는 선행 읽기에 포함하지 않는다.
- 작업: dev 서버와 API 실행 방법, 테스트 계정, 사용 가능한 브라우저 도구를 확인한다. 현재 작업 트리와 기존 검사 실패를 기록한다.
- 대표 화면: 홈, 게시판 목록/상세/작성, 행사, 달력, 설문 참여, 투표, 마이페이지, 관리자 사용자/설문 편집.
- 각 화면을 390×844와 1440×900에서 먼저 기록하고, 위험 화면은 320px·768px·1024px도 확인한다.
- 산출물: `docs/MOBILE_RESPONSIVE_AUDIT_2026-09-07.md`. route, viewport, 로그인/언어 상태, 관찰 근거, 버그/사용성/시각 품질 분류, 유지/개선/재설계 판정, 우선순위, 담당 M번호, 스크린샷 경로를 기록한다.
- 완료: 추정과 관찰 사실을 구분하고 모든 현재 route를 해당 작업 ID에 매핑한다. 기존에 모바일 구현이 있는 화면도 품질 평가에 포함한다. 접근 불가 화면은 미검증으로 표시한다.

### M00-D — 모바일 목표안과 대표 화면 설계

- 선행: M00. M01의 공통 UI 변경 전에 수행한다.
- 대표 화면: 홈, 게시판 목록/상세, 모바일 탐색 메뉴, 설문 입력, 관리자 목록 중 구조 차이가 큰 화면을 먼저 설계한다.
- 화면별 핵심 사용자 행동, 우선 정보, 목표 레이아웃, 공통으로 묶을 패턴을 정한다. 유지/개선/재설계 판정과 근거를 명시한다.
- 재설계 후보에는 기존안과 목표안을 작성하고 구조 선택이 모호한 경우에만 대안 하나를 더 비교한다. 목표안은 390px 시안/로컬 프로토타입과 320px·768px 배치 규칙으로 구체화한다.
- 메뉴 구조, 목록의 정보 위계, 입력/상세 화면, 하단 고정 액션 사용 여부, 색·타이포·여백 토큰을 하나의 모바일 디자인 방향으로 정리한다.
- 성공 기준은 화면별로 기록한다. 예: 메뉴의 목적지를 쉽게 구분할 수 있음, 중요한 공지/마감 정보가 첫 읽기 흐름에 포함됨, 작성 액션을 찾는 스크롤 감소, 표형 문항의 가로 왕복 조작 제거, 선택 상태 식별 개선.
- 산출물: `docs/MOBILE_DESIGN_DIRECTION_2026-09-07.md`와 대표 목표안. 기존안의 불편/품질 한계, 목표 구조, 전후 비교 기준, 적용 M번호, 공통 컴포넌트 변경 범위, 회귀 위험을 기록한다.
- 완료: 구현할 목표안이 선택되어 다음 단계에서 Luna가 화면 구조를 다시 추측할 필요가 없다. 사용자에게 비교 결과를 공유하되, 이미 허용된 모바일 재설계를 다시 승인받는 절차로 만들지 않는다.

- 소개: 조직도·공약·연락 정보·제휴 이미지를 읽기 순서에 맞게 배치한다.
- 로드맵: 과목 목록·그룹 탐색·필터·상세 시트·선수 과목 관계 요약을 비교한다. 모바일 그래프도 관계 이해에 도움이 되고 터치 탐색이 검증되면 후보에 포함한다. 현재 목록이 있다는 이유로 재설계를 제외하지 않는다.
- 로그인 콜백, 권한 안내, 404, 약관·개인정보 페이지의 긴 내용과 복귀 액션도 포함한다.
- 완료: 한국어·영어에서 누락된 탐색 경로 없이 각 상세와 복귀 동작이 가능하다.

### M10 — 관리자 공통 구조와 목록

- 주요 파일: `components/organisms/admin-layout.tsx`, `admin-sidebar.tsx`, `components/ui/admin-page.tsx`, `admin-data-table.tsx`, 관리자 목록 feature.

- 관리자 목적지를 업무별로 묶은 메뉴/드로어를 기존 가로 메뉴와 비교한다. 현재 위치와 다른 업무로의 전환이 더 명확하면 탐색 구조를 교체한다.
- 업무별로 표 또는 요약 목록+상세를 선택한다. 여러 행의 값 비교가 핵심이면 내부 가로 스크롤 표를 유지할 수 있고, 개별 대상 조회·처리가 핵심이면 목록 구조를 새로 설계할 수 있다. 요약에서 줄인 정보는 상세에서 접근 가능하게 한다.
- 전체선택·개별선택·일괄 액션·정렬·검색 상태는 기존 로직을 재사용한다. 모바일에서 일괄 액션이 검색이나 선택 체크박스를 가리지 않게 한다.
- 완료: 가로 스크롤은 표 내부에 한정되고 선택 → 상세 → 수정/확인 흐름이 가능한 상태다. 각 관리 권한별 메뉴 노출을 유지한다.

### M11 — 관리자 편집·복잡한 입력 화면

- 주요 파일: 관리자 설문/투표 editor, `question-editor-modal.tsx`, `section-editor-modal.tsx`, `features/admin-site-content/*`, `pages/admin/bulk-email-page.tsx`, 관리자 일정/로드맵 편집, 필요 공통 UI.

- 현재 순서 변경 기능이 drag만 제공되면 터치 스크롤과의 충돌을 확인하고 위/아래 이동 등 대체 조작을 제공한다. 서버의 순서 저장 계약은 유지한다.
- 완료: 조회뿐 아니라 편집과 저장까지 테스트 계정/로컬 데이터에서 수행할 수 있다. 발송·결제·운영 데이터 삭제 같은 실제 외부 부수 효과는 QA에 사용하지 않는다.

### M12 — 전체 회귀 검증·인계

- M00 목록의 각 문제를 해결/미해결/미검증으로 갱신한다. 구현 변경이 필요한 항목은 해당 M단계로 돌아가 고친다.
- M00-D의 화면별 개선 목표를 전후 화면과 실제 조작으로 확인한다. 재설계가 채택된 화면은 반응형 버그가 없다는 이유만으로 완료 처리하지 않는다. 유지 판정 화면도 유지 근거를 기록한다.
- 공개·인증 화면과 모든 관리자 route에 최소 390px 렌더링 검증을 수행한다. 공통/고위험 화면은 아래 전체 폭과 상태 조합을 확인한다.
- 산출물: 검증 로그·전후 스크린샷·미검증 환경·남은 문제·다음 작업을 감사 문서에 기록한다.
- 완료: 차단/높은 우선순위 UI 문제가 없고, 실제 실행한 검사 결과와 남은 검증 범위가 명확하다. 실기기 미검증을 완료로 바꾸어 기록하지 않는다.

## 5. 검증 방법

### 화면 조합

| 목적 | 크기/조건 |
|---|---|
| 최소 폭 | 320×740 |
| 일반 모바일 | 360×800, 390×844, 430×932 |
| 가로 모바일 | 844×390 |
| 태블릿 | 768×1024, 820×1180 |
| 중간 데스크톱 | 1024×768, 1280×720 |
| 데스크톱 회귀 | 1440×900 |
| 경계값 | 관련 화면에 한해 639/640, 767/768, 1023/1024, 1279/1280px |
| 확대/입력 | 브라우저 200% 확대, 키보드 Tab 탐색, 모바일 키보드, 세로/가로 회전 |

- 모든 페이지에 모든 조합을 반복하지 않는다. 전체 route는 390px에서 확인하고, 공통 변경은 대표 화면의 전체 폭에서 검증한다.
- 브라우저 자동 검증은 사용 가능한 Chromium부터 구성한다. WebKit 검증은 사용 가능한 실행 환경에서 수행하고 iOS Safari 실기기 검증과 구분한다.
- 최종 확인에 Android Chrome과 iOS Safari의 실제 키보드·주소창·safe area 동작을 포함한다. 사용할 수 없으면 필요한 검증 항목을 남긴다.
- 이미지와 폰트 로딩, API 상태를 기다린 뒤 스크린샷을 비교한다. 다른 데이터와 시각 조건 때문에 생긴 차이를 레이아웃 회귀로 오인하지 않는다.
- 모바일의 의도된 시각 변화는 기존 스크린샷과 다르다는 이유로 실패 처리하지 않는다. M00-D 목표안에 대한 완성도와 기능 회귀를 나누어 평가한다. 데스크톱은 의도하지 않은 변화가 없는지 확인한다.

### 코드 검사

저장소 루트에서 실행한다. 공유 패키지가 준비되지 않았다면 먼저 `pnpm build:shared`를 실행한다.

```sh
pnpm --filter @soc/web typecheck
pnpm --filter @soc/web lint
pnpm --filter @soc/web build
pnpm --filter @soc/web test
```

- 각 단계: 타입·lint, 변경 화면의 모바일/데스크톱 렌더링, 해당 상호작용 확인.
- 공통 UI·폼 상태를 바꾼 단계: 관련 기존 테스트와 빌드를 추가로 실행한다.
- 최종 M12: 위 web 검사 전체 실행. 기존 실패와 이번 변경에 의한 실패를 구분한다.
- 새 자동 테스트는 메뉴/모달의 포커스·잠금, 폭 변경 시 설문 값 보존, 실제 가로 넘침 같은 행동에 집중한다. CSS 클래스 이름이나 구현 문자열 일치만 검사하는 테스트는 만들지 않는다.
- E2E 도구 추가가 필요하면 기존 Node 테스트와 별도로 구성한다. 실행하지 않은 검사나 준비되지 않은 브라우저를 통과로 보고하지 않는다.
